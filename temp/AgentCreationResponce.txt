Коротко: **полностью “один агент сам создаёт двух агентов, раздаёт им права и пишет им в чаты” в OpenCode как штатная готовая функция обычно не делается**. Но такую схему **можно собрать**, если использовать заранее созданные агентские профили + инструменты вызова CLI/API/MCP + внешние ограничения прав.

Ниже — практический разбор.

---

## 1. Может ли агент “создать” других агентов?

### Из коробки обычно лучше делать не “создание”, а “вызов заранее созданных агентов”

То есть вы один раз определяете, например:

- `controller` — контролёр/оркестратор;
- `executor` — исполнитель;
- опционально `reviewer`, `tester`, `planner` и т.д.

А затем главный агент может:

- переключаться на них вручную;
- запускать их через CLI;
- вызывать их через MCP-инструмент;
- передавать им задачу через файл, JSON, очередь, базу, API.

Пример желаемой команды:

```text
Создай для проекта двух агентов: контролер и исполнитель, передай им задачи, контролируй.
```

В надёжном варианте это должно означать не “ИИ сам придумал и породил новые процессы с произвольными правами”, а:

```text
Возьми заранее подготовленные профили controller и executor,
запусти executor в ограниченной рабочей папке,
передай ему задачу,
получи результат,
проверь его.
```

---

## 2. Можно ли сделать сценарий “контролёр + исполнитель”?

Да, это реалистично.

### Рекомендуемая архитектура

```text
controller
   │
   │ ставит задачу
   ▼
executor
   │
   │ пишет код/файлы только в разрешённой области
   ▼
controller
   │
   │ проверяет diff, тесты, логи
   ▼
человек подтверждает merge / запись / деплой
```

### Важный принцип

**Контролёр не должен сам иметь право писать код.**  
Иначе он перестаёт быть контролёром и становится вторым исполнителем.

Лучше так:

| Агент | Права |
|---|---|
| `controller` | чтение, анализ, запуск проверок, вызов инструментов оркестрации |
| `executor` | запись только в рабочую ветку/worktree, ограниченный bash |
| `reviewer` | только чтение, запуск тестов, анализ diff |
| `human` | финальное разрешение на merge/deploy/опасные операции |

---

## 3. Как передавать задачи между агентами?

Есть несколько вариантов.

---

### Вариант A. Через файлы проекта

Самый простой и понятный способ.

Создаёте структуру:

```text
.agents/
  tasks/
    inbox-executor/
    inbox-controller/
    done/
    failed/
  state/
  logs/
```

Контролёр пишет задачу:

```json
{
  "task_id": "task-001",
  "title": "Добавить валидацию email",
  "allowed_paths": [
    "src/validators/",
    "tests/validators/"
  ],
  "description": "Добавить функцию validateEmail и тесты к ней.",
  "acceptance_criteria": [
    "npm test проходит",
    "нет изменений вне src/validators и tests/validators"
  ]
}
```

Исполнитель читает задачу, выполняет, пишет результат:

```json
{
  "task_id": "task-001",
  "status": "done",
  "branch": "task-001-email-validation",
  "files_changed": [
    "src/validators/email.ts",
    "tests/validators/email.test.ts"
  ],
  "tests": "passed",
  "notes": "Добавлены граничные тесты."
}
```

Контролёр читает результат и проверяет.

Плюсы:

- просто;
- легко отлаживать;
- есть история;
- не нужен сложный API.

Минусы:

- нужно самому сделать watcher/runner;
- нет мгновенной доставки в UI.

---

### Вариант B. Через CLI OpenCode

Если ваш `opencode` поддерживает запуск в неинтерактивном режиме и выбор агента, то контролёр может вызывать исполнителя через bash/MCP.

Примерно:

```bash
opencode run \
  --agent executor \
  --dir ./worktrees/task-001 \
  "Выполни задачу из файла .agents/tasks/task-001.json"
```

Или, если у вас другая версия/флаги:

```bash
opencode run "Прочитай .agents/tasks/task-001.json и выполни задачу"
```

Точные флаги нужно смотреть в вашей версии:

```bash
opencode --help
opencode run --help
opencode serve --help
```

Плюсы:

- близко к “настоящему” запуску агента;
- можно запускать в отдельной папке;
- удобно оборачивать в скрипт.

Минусы:

- нужно заранее проверить, какие флаги поддерживаются;
- надо контролировать таймауты и зависания;
- не всегда видно живое сообщение в чате другой сессии.

---

### Вариант C. Через MCP-сервер оркестрации

Это самый правильный путь, если вы хотите полноценный “менеджер агентов”.

Вы делаете свой MCP-сервер, который предоставляет инструменты:

```text
create_task
assign_task
run_executor
get_task_status
read_executor_output
approve_task
reject_task
request_permission
```

Тогда контролёр использует их как обычные tools.

Пример инструментов:

```json
{
  "name": "run_executor",
  "arguments": {
    "task_id": "task-001",
    "agent": "executor",
    "working_dir": "./worktrees/task-001",
    "timeout_seconds": 1800
  }
}
```

Или:

```json
{
  "name": "send_message_to_agent",
  "arguments": {
    "agent_session": "executor-session-123",
    "message": "Проверь замечания и исправь тесты."
  }
}
```

Внутри MCP-сервер уже сам решает:

- запускать `opencode run`;
- обращаться к HTTP API OpenCode, если он есть;
- писать в очередь;
- создавать git worktree;
- проверять права доступа;
- логировать действия.

Плюсы:

- самый управляемый вариант;
- можно сделать нормальные права;
- можно сделать очередь задач;
- можно писать в разные сессии, если есть API.

Минусы:

- нужно писать код;
- нужно следить за безопасностью.

---

## 4. Может ли контролёр “выдавать разрешения на чтение и запись в папках”?

Здесь важно разделять два уровня.

---

### 1. Разрешения внутри OpenCode

Если OpenCode в вашей версии поддерживает настройки прав для агентов, то лучше задавать их **заранее в конфигурации**, а не давать ИИ менять их во время работы.

Условно:

```json
{
  "agents": {
    "controller": {
      "description": "Планирует и проверяет",
      "permissions": {
        "edit": "deny",
        "bash": "ask"
      }
    },
    "executor": {
      "description": "Выполняет изменения",
      "permissions": {
        "edit": "allow",
        "bash": "ask"
      }
    }
  }
}
```

Синтаксис зависит от версии OpenCode, но суть такая:

- одному агенту можно запретить редактирование;
- другому разрешить;
- третьему разрешить только чтение;
- bash лучше делать через подтверждение или ограниченный whitelist команд.

---

### 2. Настоящие файловые права

Если вам нужно реально ограничить доступ к папкам, лучше не полагаться только на промпт или настройки агента.

Надёжнее использовать:

- отдельную рабочую папку;
- git worktree;
- отдельного ОС-пользователя;
- контейнер;
- chroot/namespace;
- Docker/Podman;
- MCP-filesystem-сервер с whitelist путей;
- файловые права ОС.

Пример безопасного подхода:

```text
project/
  worktrees/
    task-001/
    task-002/
```

Исполнитель запускается только внутри:

```text
project/worktrees/task-001/
```

Контролёр читает diff оттуда, но сам не пишет.

---

## 5. Может ли ИИ писать в другую сессию сообщения непосредственно в чат?

### Напрямую, как “нативный инструмент” — обычно нет

То есть модель не имеет стандартного инструмента вида:

```text
написать_в_чат_другой_сессии("Привет, проверь задачу")
```

Если только в вашей версии OpenCode специально не реализован межсессионный API/message bus.

---

### Когда это возможно

Это возможно, если есть один из механизмов:

1. **CLI-команда отправки сообщения в сессию**  
   Например что-то вроде:

   ```bash
   opencode send --session <session-id> "сообщение"
   ```

   или:

   ```bash
   opencode run --session <session-id> "сообщение"
   ```

   Но наличие такой команды нужно проверять в вашей версии.

2. **HTTP/API-сервер OpenCode**  
   Если OpenCode умеет работать как сервер, например:

   ```bash
   opencode serve
   ```

   тогда агент через bash/MCP может делать запросы:

   ```bash
   curl -X POST http://localhost:PORT/sessions/<id>/messages \
     -H 'Content-Type: application/json' \
     -d '{"message": "Проверь задачу task-001"}'
   ```

   Опять же: конкретный endpoint зависит от версии.

3. **Ваш MCP-сервер**  
   Вы сами делаете инструмент:

   ```text
   send_message_to_session
   ```

   который внутри пишет в нужную сессию через API, базу, очередь, tmux, webhook и т.д.

---

### Когда это возможно “грязно”, но нежелательно

Если у агента есть доступ к bash, он теоретически может:

- найти процесс OpenCode;
- использовать tmux `send-keys`;
- писать в stdin процесса;
- эмулировать клавиши;
- подменять файлы сессии.

Но это плохой путь:

- небезопасно;
- нестабильно;
- ломается при обновлении;
- может привести к самопроизвольным действиям;
- сложно аудировать.

Для продакшена так лучше не делать.

---

## 6. Что я рекомендую сделать конкретно для вашей задачи

### Минимальная безопасная схема

Сделайте так:

1. Создайте агентов заранее:
   - `controller`;
   - `executor`.

2. Для исполнителя выделите отдельный git worktree:

   ```bash
   git worktree add ../project-task-001 -b task-001
   ```

3. Контролёр может только:
   - читать файлы;
   - создавать задачи;
   - запускать исполнителя через скрипт;
   - читать результат;
   - запускать тесты;
   - просить человека подтвердить изменения.

4. Исполнитель может:
   - редактировать только свой worktree;
   - запускать только разрешённые команды;
   - писать отчёт о выполнении.

5. Финальное разрешение делает человек:
   - merge;
   - deploy;
   - удаление веток;
   - запись в защищённые папки;
   - доступ к секретам.

## 7. Пример логики контролёра

Промпт для `controller` может быть примерно таким:

```text
Ты — контролёр проекта.

Ты не редактируешь код напрямую и не выполняешь опасные команды.

Твоя работа:
1. Принять цель от пользователя.
2. Разбить её на задачи.
3. Для каждой задачи вызвать инструмент run_executor.
4. Получить результат от исполнителя.
5. Проверить:
   - изменены только разрешённые файлы;
   - тесты проходят;
   - нет неожиданных изменений;
   - задача соответствует acceptance criteria.
6. Если задача не выполнена — вернуть исполнителю замечания.
7. Если задача выполнена — подготовить итоговый отчёт для человека.

Ты не выдаёшь новые права самостоятельно.
Если нужны дополнительные права, создай запрос на подтверждение пользователю.
```

Промпт для `executor`:

```text
Ты — исполнитель задачи.

Работай только в текущей рабочей директории.
Не выходи за пределы разрешённых путей.
Не меняй конфигурацию, секреты, CI, git hooks и системные файлы, если это явно не разрешено задачей.

После выполнения задачи создай отчёт:
- что сделано;
- какие файлы изменены;
- какие команды запускались;
- результаты тестов;
- известные риски.
```

## 8. Пример задачи для передачи исполнителю

Лучше передавать задачу структурированно, а не просто текстом.

```json
{
  "task_id": "task-001",
  "agent": "executor",
  "working_directory": "./worktrees/task-001",
  "goal": "Добавить endpoint /healthz",
  "allowed_paths": [
    "src/routes/",
    "tests/routes/"
  ],
  "forbidden_paths": [
    ".env",
    "package-lock.json",
    ".github/",
    "scripts/deploy/"
  ],
  "commands_allowed": [
    "npm test",
    "npm run lint"
  ],
  "acceptance_criteria": [
    "endpoint /healthz возвращает 200",
    "добавлен тест",
    "npm test проходит"
  ],
  "report_to": ".agents/tasks/done/task-001.result.json"
}
```

Это намного надёжнее, чем просто:

```text
Сделай endpoint /healthz
```

## 9. Можно ли сделать “динамическое создание агентов”?

Технически можно, но я бы не рекомендовал делать это полностью динамически без человека.

Например, агент может:

1. Создать файл нового агента.
2. Записать его промпт.
3. Задать разрешения.
4. Попросить OpenCode перечитать конфиг.
5. Запустить нового агента.

Но тут много проблем:

- OpenCode может не подхватить нового агента без перезапуска;
- агент может сам себе выдать лишние права;
- сложно понять, кто что сделал;
- появляется риск privilege escalation;
- нужно контролировать время жизни таких агентов.

Лучше использовать пул заранее одобренных агентов:

```text
controller
executor
reviewer
tester
docs-writer
security-auditor
```

А “создать агента” в пользовательском смысле пусть означает:

```text
создать новый экземпляр/сессию уже существующего агента
```

а не:

```text
породить новый тип агента с новыми правами
```

## 10. Итоговый ответ на ваши вопросы

### 1. Может ли один агент создать двух агентов: контролёра и исполнителя?

**Частично да, но лучше не “создать с нуля”, а запустить заранее настроенные профили.**

Полностью автономное создание агентов с произвольными правами — небезопасно и обычно требует внешней обвязки: CLI, MCP, скриптов, API.

---

### 2. Может ли он передать им задачи и контролировать?

**Да, если есть механизм передачи задач и получения результата.**

Самые практичные способы:

- файлы задач;
- JSON-очередь;
- запуск `opencode run` из bash;
- MCP-инструмент оркестрации;
- HTTP API, если OpenCode его предоставляет.

---

### 3. Может ли он выдавать разрешения на чтение и запись в папках?

**Только если это разрешено архитектурой, но лучше так не делать.**

Правильнее:

- права задаёт человек заранее;
- агент может только запросить расширение прав;
- человек подтверждает;
- реальные ограничения делаются через конфиг, ОС, контейнер, git worktree или MCP-сервер.

---

### 4. Может ли ИИ писать в другую сессию сообщения непосредственно в чат?

**Напрямую из коробки — скорее всего нет, если нет специального API/IPC.**

Возможно, если:

- есть `opencode serve` / HTTP API;
- есть CLI-команда отправки сообщения в сессию;
- вы сами сделали MCP-инструмент для межсессионной доставки;
- вы используете внешний оркестратор.

Без этого агент может общаться с другой сессией только косвенно:

- через файлы;
- через базу;
- через очередь;
- через запуск новой CLI-команды;
- через логи.

---

## 11. Практический минимум, с которого можно начать

Сделайте так:

```text
.agents/
  config/
    controller.md
    executor.md
  tasks/
    pending/
    done/
    failed/
  logs/
```

Затем:

1. Запускаете основную сессию как `controller`.
2. Даёте ему право читать `.agents/tasks/`.
3. Даёте ему инструмент запуска скрипта:

```bash
./scripts/run-executor.sh .agents/tasks/pending/task-001.json
```

4. Скрипт:
   - создаёт git worktree;
   - запускает `opencode run` с агентом `executor`;
   - сохраняет вывод в `.agents/logs/`;
   - кладёт результат в `.agents/tasks/done/`.

5. Контролёр читает результат и решает:
   - принять;
   - вернуть на доработку;
   - попросить человека.

Это даст вам управляемую multi-agent схему без опасной магии.
