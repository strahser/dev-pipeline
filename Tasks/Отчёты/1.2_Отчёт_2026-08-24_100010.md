# ОТЧЁТ: 1.2 — Бюджет рестартов по родословной, а не по sid

Дата: 2026-08-24 10:00:10 → исполнено 2026-08-24.
Статус: **done**.

## Что было не так (факт по коду)

1. `pipeline\crew.py:plan_restarts` вёл счётчики рестартов **по sid**
   (`counters.setdefault(sid, {"count": 0, ...})`). Каждый рестарт создаёт
   НОВУЮ сессию (новый sid) со свежим счётчиком → лимит `max_restarts`
   был недостижим по цепочке поколений: S1→S2→S3… могло длиться бесконечно.
2. Следствие: упавшая сессия остаётся `failed` в БД навсегда и на КАЖДОМ
   проходе супервизора снова получала решение `restart` — дубли порций той же
   работы размножались каждый тик (шторм «морг из десятков сессий» вместе
   с багом 1.1).
3. Cooldown считался от последнего рестарта конкретного sid, а не цепочки;
   после перезапуска процесса супервизора локальный кэш counters терялся.

## Что сделано

`pipeline\crew.py`:
- Константы `RESTARTS_KEY = "_restarts"` и `RESTART_TS_KEY = "_restart_ts"` —
  родословная цепочки едет В instruction сессии (критерий приёмки №1,
  «или эквивалент» реализован именно так).
- Новый помощник `_chain_state(s, counters)`: счётчик и время последнего
  рестарта берутся из `instruction._restarts/_restart_ts` новой сессии
  (родословная сильнее локального кэша), запись `counters[sid]` синхронизируется
  как кэш + хранение флагов.
- `plan_restarts`: бюджет `max_restarts` считается ПО ЦЕПОЧКЕ (`count >= max_n`
  → `exhausted`); cooldown — от последнего рестарта цепочки (`_restart_ts`);
  сессии с флагом `handled` (уже породившие преемника или объявленные
  exhausted) больше не рассматриваются — дубли порций исключены.
- `supervise_once`: при рестарте новая сессия получает
  `instruction{_restarts: родитель+1, _restart_ts: ts}` (вместе с промптом и
  handoff-хвостом); `counters[new_sid]` инициализируется тем же бюджетом;
  родитель помечается `handled=True` только при УСПЕШНОМ создании преемника
  (при сбое создания бюджет не сгорает — ретрай следующего тика);
  `crew_exhausted` уходит в ленту РОВНО ОДИН раз на цепочку (флаг до notify).

`agents\project_manager.py`, `pipeline\cli.py` (cmd_supervise) изменений не
требуют — оба уже передают один общий dict counters сквозь тики; наследование
живёт в instruction сессий на сервере (БД хранит instruction как произвольный
JSON — схема не менялась).

## Доказательства

```
python -X utf8 tests/test_crew.py -v   →  Ran 25 tests ... OK
python -X utf8 tests/run_all.py        →  Ran 204 tests in 35.201s ... OK (0 падений)
```

Новые тесты (tests\test_crew.py, класс RestartChainTest):
1. `test_counter_travels_with_instruction` — новое поколение S2 при ПУСТОМ
   counters: cooldown от `_restart_ts`; при `_restarts=2 >= max_restarts` —
   exhausted (родословная без локального кэша).
2. `test_chain_S1_to_S2_to_exhausted` — полный цикл критерия №3/№4:
   S1 failed → restart S2 (`_restarts=1`) → S2 failed → restart S3
   (`_restarts=2`) → S3 failed → **exhausted**, новых сессий больше нет,
   `crew_exhausted` ровно 1 раз; тик 4 — полная тишина (0 решений, 0 событий).
3. `test_handoff_continuation_inherits_budget` — продолжение по handoff
   наследует тот же бюджет цепочки (`_restarts=1`) и получает хвост handoff.
4. `test_cooldown_from_last_chain_restart` — cooldown считается от момента
   последнего рестарта ЦЕПОЧКИ через supervise_once (1200с < 1000с+300с →
   cooldown; 1300с ≥ → restart).
Старые тесты PlanRestartsTest/SuperviseOnceTest/ManagerTest прошли без правок
(обратная совместимость: сессии без `_restarts` ведутся по counters, как раньше).
