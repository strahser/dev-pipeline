# ОТЧЁТ: 4.2 — Динамическая выдача прав записи (API + CLI)

Дата: 2026-08-24
Статус: done

## Что было не так

`ensure_permissions` (pipeline/crew.py) создавал профиль прав `.opencode/permissions.json`
один раз и «существующий не трогал»: сменить режим read/write можно было только руками
в файле, события в ленте не было. Разрыв с целевым сценарием «менеджер даёт разрешение
на запись, если нужно».

## Что сделано

1. **pipeline/crew.py** — новые функции:
   - `set_permissions(cfg, mode)` — перезаписывает `.opencode/permissions.json`
     шаблоном `permissions_template(mode)`; невалидный mode (`не read|write`) →
     `ValueError`.
   - `read_permissions(cfg)` — текущий режим из файла (`edit: allow` → write, иначе read;
     файла нет → None).
2. **server/app.py** — эндпоинт `PUT/POST /api/projects/{project}/permissions`
   (`{"mode": "read"|"write"}`):
   - перезаписывает профиль через `crew.set_permissions`;
   - публикует событие `permissions_changed` (payload: mode + относительный путь к файлу);
   - ответ включает итоговый профиль;
   - невалидный mode → 400, неизвестный проект → 404.
   Попутный фикс: добавлен `import json` на уровне модуля (эндпоинт его использует,
   а был только локальный `import json as _j` внутри `_sse`).
3. **pipeline/cli.py** — команда `perms`:
   `python -m pipeline.cli perms <project> read|write`;
   невалидный mode → ошибка + rc=1.
4. **AGENTS.md** (правила) — добавлено правило консервативного дефолта read:
   write выдаёт владелец/менеджер-агент динамически (API или CLI) на время задачи;
   сессии подхватывают профиль при старте порции (tui_cycle/up); по завершении —
   возврат в read.
5. **Тесты**:
   - `tests/test_crew.py` — класс `SetPermissionsTest`: set write→read перезаписывает
     файл, невалидный mode → ValueError, отсутствующий файл → read_permissions None.
   - `tests/test_server.py` — класс `PermissionsEndpointTest`: PUT write меняет файл +
     событие permissions_changed, POST read меняет файл, невалидный mode → 400,
     неизвестный проект → 404.
   - `tests/test_cli_smoke.py` — `cmd_perms write` создаёт/перезаписывает файл,
     невалидный mode → rc != 0.

## ASSUMPTION

- ASSUMPTION: `set_permissions` перезаписывает файл шаблоном целиком и не сохраняет
  посторонние ключи (например, `external_directory`, добавленные вручную в профиль
  реального проекта devpipeline). Это соответствует букве карточки («перезаписывает
  crew.permissions_template») и критерию приёмки 1. После демонстрации CLI исходный
  профиль реального проекта с `external_directory` восстановлен вручную — карточка
  не меняет действующий профиль работающего конвейера.

## Открытые вопросы и ограничения

- `permissions_template` не содержит `external_directory`: если проект держит такие
  ключи в своём `.opencode/permissions.json`, смена режима их затрёт. Решение — либо
  считать файл каноном (как сейчас), либо расширить шаблон. Предложено в ASSUMPTION.
- Действующий профиль реального проекта devpipeline на момент отчёта возвращён
  к исходному состоянию (write + external_directory), чтобы не ломать работающий
  план-раннер.
