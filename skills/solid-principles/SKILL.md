# SOLID Principles Skill

Ты помогаешь с кодом, который должен строго следовать принципам SOLID.

## Принципы для применения

### 1. Single Responsibility Principle (SRP)
- У каждого класса ОДНА причина для изменения
- Каждая функция делает ОДНО дело хорошо
- Разделяй: бизнес-логика, доступ к данным, представление, валидация
- Если имя класса содержит «and»/«or» — вероятно нарушение SRP

**Red flags:**
- Классы с множеством несвязанных методов (god-object)
- Функции, делающие несколько операций
- Смешение забот (валидация + персистентность в одном методе)

### 2. Open/Closed Principle (OCP)
- Открыт для расширения, закрыт для модификации
- Абстрактные базовые классы и интерфейсы для расширяемости
- Композиция предпочтительнее наследования
- Новые фичи добавляются расширением, а не правкой существующего кода

**Паттерны:**
- Strategy — для варьирующихся алгоритмов
- Template Method — для варьирующихся шагов
- Dependency Injection — для варьирующихся реализаций

### 3. Liskov Substitution Principle (LSP)
- Подтипы должны быть подставляемы вместо базовых типов
- Производные классы не должны усиливать предусловия
- Производные классы не должны ослаблять постусловия
- НЕТ пустых реализаций и NotImplementedError/NotSupportedException в проде

**Правила:**
- Не переопределяй методы «в никуда» (throw/пусто)
- Соблюдай контракты поведения
- Композиция, когда наследование не подходит естественно

### 4. Interface Segregation Principle (ISP)
- Клиенты не должны зависеть от интерфейсов, которые не используют
- Сфокусированные, связные интерфейсы/абстрактные классы
- Много маленьких интерфейсов > один большой
- Избегай «жирных» базовых классов с множеством опциональных методов

**Реализация:**
- Дроби большие интерфейсы на ролевые
- Избегай методов, которые часть клиентов не использует (пустые/throw)

### 5. Dependency Inversion Principle (DIP)
- Модули верхнего уровня не зависят от модулей нижнего
- Оба зависят от абстракций (интерфейсы, абстрактные классы)
- Абстракции не зависят от деталей; детали зависят от абстракций

**Паттерны:**
- Constructor injection для обязательных зависимостей
- Зависеть от интерфейсов, а не конкретных реализаций

## Чек-лист кода (при написании/ревью)

- [ ] У каждого класса одна ясная ответственность?
- [ ] Новое поведение добавляется без правки существующего кода?
- [ ] Подклассы заменяют родителей без поломки функциональности?
- [ ] Интерфейсы сфокусированы и связны?
- [ ] Модули зависят от абстракций, а не от конкретных реализаций?

## Практическое применение в проектах конвейера (HeatLossRevit2, C# net48)

Архитектура плагина уже задаёт слои: `Core` (бизнес-логика) → `RevitServices` (мост) → `MainAppHeatLoss` (composition root). SOLID применяется ВНУТРИ этих слоёв:

- **SRP**: не мешай в одном классе расчёт теплопотерь + чтение параметров Revit + запись результатов; перенос кода между слоями — только по границам архитектуры.
- **OCP**: новые типы расчётов/правил — через интерфейсы и регистрацию в DI (перечисление типов через switch по типу — red flag), а не правкой ядра.
- **LSP**: все реализации интерфейса должны быть взаимозаменяемы; заглушки «throw NotSupportedException» в прод-коде — нарушение.
- **ISP**: интерфейсы расчёта/экспорта/валидации — раздельные и ролевые; DI-модули регистрируют именно их.
- **DIP**: Core зависит от абстракций из Base/Core (не от Autodesk.Revit и не от конкретных экспортёров); конкретику подключает composition root (MainAppHeatLoss).

Границы слоёв (AGENTS.md проекта) приоритетнее отдельных принципов: если SOLID-правка требует ссылки из Core на Autodesk.Revit — это запрещено, решай через интерфейсы и мост.

## Формат ответа

При применении SOLID:
1. Укажи, какие принципы релевантны
2. Объясни нарушение (если есть)
3. Дай рефакторинг по принципу(-ам)
4. Объясни выгоду
