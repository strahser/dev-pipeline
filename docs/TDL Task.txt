# Агентное задание: планирование и отслеживание задач по Revit-проектам в TDL

## 1. Цель задания

ИИ-агент должен вести таблицу задач TDL по Revit-проектам так, чтобы:

1. Любая работа была декомпозирована до атомарных, проверяемых задач.
2. У каждой задачи были понятные входные данные, цель, результат, ссылки и сроки.
3. Агент не мог заявить «выполнено» без фактических доказательств.
4. Пользователь мог в любой момент открыть карточку задачи, перейти по гиперссылкам и оценить результат: аналитическая записка, DWF-чертёж, Three.js-сцена, тестовый отчёт, скриншот, лог, commit и т.д.
5. TDL была пригодна для фильтрации, контроля сроков, статусов и этапной отчётности.

# 2. Жёсткие правила для агента

Эти правила являются обязательными. Агент не имеет права их обходить.

## 2.1. Структура планирования

1. Планирование выполняется только через **СДР** — структуру декомпозиции работ.
2. Максимальная вложенность СДР — **4 уровня**.
3. Суммарные задачи используются только как **extender** в UI: для группировки и отображения этапности.
4. Суммарная задача **не является исполнительским элементом**:
   - агент не назначает её как работу;
   - агент не закрывает суммарную задачу вручную;
   - агент не ставит для неё фактическое исполнение;
   - статус суммарной задачи может быть только производным от дочерних листьев.
5. Планировать, выполнять и переводить в «Выполнено» можно только **листовые задачи**.

## 2.2. Статусы

Используются только два статуса:

| Статус | Значение |
|---|---|
| `Открыто` | Задача в работе, ожидает данных, заблокирована, ещё не начата или не имеет доказательств выполнения |
| `Выполнено` | Задача закрыта только при наличии полного набора доказательств |

Если агент не может выполнить задачу, он **не имеет права** ставить «Выполнено». Вместо этого задача остаётся `Открыто`, а в карточке фиксируется блокировка и причина.

## 2.3. Запрет на ложь

Агенту запрещено:

1. Писать «выполнено», «готово», «проверено», «работает» без ссылок на доказательства.
2. Закрывать задачу без:
   - гиперссылки на результат;
   - отчётного документа или артефакта;
   - тестового лога, скриншота, DWF, Three.js, commit, файла, JSON-отчёта или другого подтверждения.
3. Заменять доказательства текстовыми утверждениями.
4. Удалять или перезаписывать старые доказательства.
5. Менять срок без комментария и истории изменения.
6. Создавать укрупнённые исполнительские задачи без декомпозиции до проверяемых листьев.
7. Использовать суммарную задачу как фактический план.
8. Начинать выполнение задачи, если у неё не заполнены:
   - цель;
   - входные данные;
   - ожидаемый результат;
   - критерии приёмки.

## 2.4. Принцип «Нет доказательства — нет выполнения»

Задача может быть переведена в `Выполнено`, только если одновременно выполнены все условия:

1. Задача является листовой.
2. Заполнены все обязательные поля.
3. Есть гиперссылка на результат.
4. Есть отчётный документ или артефакт этапа.
5. Есть доказательство проверки:
   - тест пройден;
   - или есть скриншот;
   - или есть DWF/Three.js;
   - или есть аналитическая записка;
   - или есть commit/PR;
   - или есть лог выполнения.
6. Дата завершения соответствует фактической дате предоставления результата.
7. Изменение статуса записано в audit log.

# 4. Правила заполнения СДР

## 4.1. Уровни СДР

Рекомендуемая структура:

| Уровень | Назначение | Пример |
|---|---|---|
| 1 | Этап проекта | `1` — Снимок модели Revit |
| 2 | Подэтап / модуль / функциональный блок | `1.1` — Получить количество видовых экранов |
| 3 | Класс / рабочий пакет / сервис | `1.1.1` — Реализовать `ViewportCollector` |
| 4 | Атомарная задача / тест / проверка | `1.1.1.1` — Тест получения количества видовых экранов |

## 4.2. Требования к leaf-задаче

Листовая задача должна быть:

1. Атомарной.
2. Измеримой.
3. Проверяемой.
4. Независимой или с явно указанными зависимостями.
5. Имеющей конкретный результат.

Плохо:

> Сделать экспорт Revit.

Хорошо:

> Реализовать метод `ViewportCollector.GetViewports()` для получения списка видовых экранов из активного Revit-документа и вернуть JSON со списком видов.

# 10. Требования к фильтрации TDL

Таблица TDL должна поддерживать фильтрацию минимум по следующим полям.

## 10.1. Обязательные фильтры

| Фильтр | Поле | Пример использования |
|---|---|---|
| Проект | `project` | Показать задачи только проекта `Revit Pilot` |
| СДР | `wbs_code` | Показать задачи ветки `1.1` |

| Наличие отчёта | `report_document exists` | Задачи без отчётного документа |

| Блокировка | `blocker not empty` | Показать заблокированные задачи |
| Проверено | `verified_by` | Показать задачи, подтверждённые `ci` или `user` |

## 10.2. Быстрые фильтры для пользователя

Рекомендуется добавить быстрые фильтры:

1. «Просроченные открытые».
2. «Без отчёта».
3. «Без доказательств».
4. «Тесты».
5. «Revit API».
6. «DWF экспорт».
7. «Three.js».
8. «Заблокированные».
9. «Задачи текущего этапа».
10. «Готово к приёмке пользователем».

# 11. Анти-ложь: протокол проверки выполненной задачи

Перед тем как агент меняет статус на `Выполнено`, он обязан пройти обязательный checklist.

## 11.1. Checklist для leaf-задачи

```text
[ ] Задача является листовой, а не суммарной.
[ ] Уникальный код СДР существует и соответствует родителю.
[ ] Заполнены project, name, description, goal.
[ ] Заполнены start_date и finish_date.
[ ] Указаны критерии приёмки.
[ ] Есть task_kind.
[ ] Есть гиперссылка на задание или источник работы.
[ ] Есть входные ссылки, если задача требует входных данных.
[ ] Есть результативная ссылка: код, файл, отчёт, DWF, Three.js, тест.
[ ] Есть отчётный документ или артефакт.
[ ] Есть доказательство выполнения.
[ ] Доказательство доступно по ссылке или пути.
[ ] Тест или проверка имеет статус passed/success.
[ ] Указано, кем проверено: agent, ci, user, second_agent.
[ ] Нет незакрытых блокировок.
[ ] История изменения статуса записана.
```

Если хотя бы один пункт не выполнен, статус должен оставаться `Открыто`.

# 14. Алгоритм работы агента

Агент обязан работать по следующему циклу.

## Шаг 1. Получить цель

Агент получает пользовательскую или проектную цель, например:

> Сделать снимок модели Revit и получить видовые экраны для тестов.

## Шаг 2. Создать этап-extender

Агент создаёт суммарную задачу уровня 1:

```text
1 Этап 1. Снимок модели Revit
```

Эта задача используется только для группировки и отчётности.

## Шаг 3. Декомпозировать до листьев

Агент создаёт задачи уровней 2–4.

Каждый лист должен иметь:

- цель;
- описание;
- входные данные;
- критерии приёмки;
- ссылки;
- сроки;
- ожидаемый результат.

## Шаг 4. Проверить готовность плана

Перед началом выполнения агент проверяет:

1. Нет пустых обязательных полей.
2. Нет дублей `wbs_code`.
3. Родительские коды существуют.
4. Уровень не выше 4.
5. Суммарные задачи не назначены как исполнительские.
6. Для всех leaf-задач есть критерии приёмки.
7. Для тестов есть входные данные и ожидаемый результат.

Если план не готов, агент не начинает выполнение.

## Шаг 5. Выполнять только leaf-задачи

Агент выполняет задачи по приоритету и зависимостям.

Если задача требует запроса данных, агент создаёт или помечает задачу как `request`.

Если задача требует кода, агент создаёт или помечает задачу как `execution`.

## Шаг 6. Собирать доказательства

Для каждой задачи агент сохраняет:

- ссылки;
- файлы;
- отчёты;
- логи;
- скриншоты;
- commit/PR;
- DWF/Three.js;
- хэши или версии.

## Шаг 7. Обновлять TDL

Агент обязан обновлять TDL сразу после изменения факта:

- создана задача;
- изменён статус;
- изменён срок;
- добавлена ссылка;
- добавлен отчёт;
- появилась блокировка;
- получено подтверждение пользователя.

## Шаг 8. Закрывать задачу только при доказательствах

Агент переводит задачу в `Выполнено`, только если выполнен полный checklist.

## Шаг 9. Сформировать этапный отчёт

После закрытия leaf-задач этапа агент формирует отчёт для пользователя:

- аналитическая записка;
- DWF;
- Three.js;
- test report;
- PDF;
- JSON-итог.

# 15. Правила работы со сроками

1. У каждой leaf-задачи должны быть `start_date` и `finish_date`.
2. У суммарной задачи сроки могут отсутствовать или вычисляться автоматически.
3. Если срок сдвигается, агент обязан указать:
   - старую дату;
   - новую дату;
   - причину;
   - дату изменения.
4. История изменения сроков должна сохраняться.
5. Просроченной считается задача:
   - статус `Открыто`;
   - `finish_date < текущая дата`.

---

# 16. Правила работы с блокировками

Если агент не может выполнить задачу, он обязан:

1. Оставить статус `Открыто`.
2. Заполнить поле `blocker`.
3. Создать отдельную задачу-запрос, если блокировка требует внешних данных.
4. Указать ссылку на недостающий документ, модель, доступ, файл или решение.
5. Не закрывать заблокированную задачу.

Пример блокировки:

```text
Блокировка: отсутствует тестовая модель sample.rvt.
Требуется: ссылка на Revit-файл или доступ к хранилищу.
Задача-запрос: 1.1.2 — Получить тестовую модель sample.rvt.
```

# 18. Связь с существующей моделью ProjectTDL

Если использовать текущую Django-модель `ProjectTDL.TaskNode`, то отображение может быть таким.

## 18.1. Текущие поля TaskNode

| Поле TDL | Существующее поле TaskNode | Комментарий |
|---|---|---|
| Наименование | `name` | Использовать как есть |

| Срок завершения | `due_date` | Завершение |
| История сроков | `TaskDueDateHistory` | Использовать для аудита сроков |
| Иерархия | `parent` / MPTT | Использовать для СДР |

## 18.2. Желательные новые поля

Для полноценной TDL лучше добавить отдельные поля:

```python
LAYER_CHOICES = [
    ('core', 'Ядро'),
    ('ui', 'UI'),
    ('infrastructure', 'Инфраструктура'),
    ('features', 'Фичи'),
    ('tests', 'Тесты'),
]

TASK_KIND_CHOICES = [
    ('group', 'Группа'),
    ('request', 'Запрос'),
    ('execution', 'Выполнение'),
]

class TaskNode(MPTTModel):
    wbs_code = models.CharField('СДР', max_length=50, unique=True, blank=True, null=True)
    module_name = models.CharField('Модуль', max_length=255, blank=True, null=True)
    class_name = models.CharField('Класс', max_length=255, blank=True, null=True)
    layer = models.CharField('Слой', max_length=20, choices=LAYER_CHOICES, blank=True, null=True)
    task_kind = models.CharField('Тип задания', max_length=20, choices=TASK_KIND_CHOICES, default='execution')
    goal = models.TextField('Цель', blank=True, null=True)
    test_inputs = models.JSONField('Входные данные теста', default=dict, blank=True)
    check_subject = models.TextField('Что проверяем', blank=True, null=True)
    acceptance_criteria = models.JSONField('Критерии приёмки', default=list, blank=True)
    start_date = models.DateField('Начало', blank=True, null=True)
    links = models.JSONField('Гиперссылки', default=dict, blank=True)
    report_link = models.URLField('Отчётный документ', blank=True, null=True)
    evidence = models.JSONField('Доказательства', default=list, blank=True)
    blocker = models.TextField('Блокировка', blank=True, null=True)
    is_summary = models.BooleanField('Суммарная задача', default=False)
    verified_by = models.CharField('Проверено', max_length=20, blank=True, null=True)
```

Если быстрые изменения модели нежелательны, часть данных можно временно хранить в `description` или отдельном JSON-поле, но для фильтрации лучше использовать отдельные поля.

# 20. Автоматические валидации

Чтобы агент не мог соврать, система должна автоматически проверять данные.

## 20.1. Валидации создания задачи

1. `wbs_code` уникален.
2. Родительский `wbs_code` существует.
3. Уровень не больше 4.
4. Если `is_summary = true`, задача не имеет исполнительских доказательств.
5. Если задача листовая, `name` начинается с глагола или явно описывает результат.
6. `project` заполнен.
7. `goal` заполнен.
8. `acceptance_criteria` содержит минимум один пункт.
9. Для `task_kind = execution` есть `task_link` или описание задания.
10. Для тестов заполнены `test_inputs` и `check_subject`.

## 20.2. Валидации закрытия задачи

1. Задача не является суммарной.
2. Заполнены `output_links`.
3. Заполнен `report_document` или есть выходной артефакт.
4. Массив `evidence` не пуст.
5. Хотя бы одно доказательство имеет `result = passed/success`.
6. Заполнен `verified_by`.
7. Нет блокировки.
8. Все зависимости имеют статус `Выполнено`, если зависимости обязательны.

## 20.3. Псевдокод проверки закрытия

```python
def can_close_task(task):
    if task.is_summary:
        return False, "Суммарную задачу нельзя закрыть вручную"

    if not task.goal:
        return False, "Не заполнена цель"

    if not task.acceptance_criteria:
        return False, "Не заполнены критерии приёмки"

    if not task.output_links:
        return False, "Нет ссылок на результат"

    if not task.evidence:
        return False, "Нет доказательств выполнения"

    if not any(e.get("result") in ("passed", "success", "approved") for e in task.evidence):
        return False, "Нет подтверждённого результата"

    if task.blocker:
        return False, "Задача заблокирована"

    return True, "OK"
```

# 21. Готовый prompt для ИИ-агента

Можно использовать следующий текст как системное задание.

```text
Ты — ИИ-агент планирования и отслеживания задач для Revit-проектов.

Твоя задача — вести таблицу TDL так, чтобы любой человек мог проверить факт выполнения каждой задачи без твоих устных объяснений.

Обязательные правила:

1. Планирование выполняется только через СДР.
2. Максимальная глубина СДР — 4 уровня.
3. Суммарные задачи используются только как extender в UI и не являются исполнительскими задачами.
4. Исполнительскими являются только листовые задачи.
5. Используются только статусы «Открыто» и «Выполнено».
6. Запрещено ставить статус «Выполнено» без доказательств.
7. Для каждой листовой задачи обязательно заполнять:
   - проект;
   - наименование;
   - описание;
   - цель;
   - входные данные;
   - критерии приёмки;
   - сроки начала и завершения;
   - задание;
   - гиперссылки;
   - ожидаемый результат.
8. Для тестов обязательно указывать входные данные и проверяемое условие.
9. Для выполненной задачи обязательно предоставить:
   - ссылку на результат;
   - отчётный документ или артефакт;
   - доказательство: тестовый отчёт, commit, DWF, Three.js, скриншот, лог, файл или пользовательскую приёмку.
10. Если доказательств нет, задача остаётся «Открыто».
11. Если задача не может быть выполнена, заполни блокировку и создай задачу-запрос.
12. Запрещено удалять доказательства или историю изменений.
13. Все изменения сроков и статусов должны сохраняться в истории.
14. Для каждого этапа формируй отчётный документ для пользователя: аналитическую записку, DWF, Three.js, PDF, тестовый отчёт или другой проверяемый артефакт.
15. В таблице TDL обеспечивай фильтрацию по проекту, СДР, модулю, классу, слою, статусу, срокам, наличию отчёта, наличию доказательств и блокировкам.
16. Каждая задача должна иметь карточку с полными данными и гиперссылками.

Твоя цель — не красиво отчитаться, а создать проверяемый, прозрачный и выполнимый план.
```

# 22. Критерии приёмки результата

Результат работы агента считается корректным, если:

1. Создана таблица TDL.
2. Есть фильтрация по проекту, СДР, модулю, классу, слою, статусу и срокам.
3. Все задачи имеют уникальные коды СДР.
4. Суммарные задачи не используются как исполнительские.
5. Все исполнительские задачи являются листьями.
6. У каждой листовой задачи есть карточка.
7. В карточке есть гиперссылки на документы и артефакты.
8. Для выполненных задач есть доказательства.
9. Для каждого этапа есть отчётный документ.
10. Ни одна задача не закрыта без фактического результата.
11. История изменений статусов и сроков сохранена.
12. Пользователь может открыть TDL, применить фильтры и сразу понять, что сделано, что не сделано и где доказательства.
