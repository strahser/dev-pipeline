Ниже — переработанный стандарт системы «задание → отчёт → вердикт» в JSON с учётом принятых TDL-правил: СДР/WBS, leaf-задачи, статусы `open/done`, обязательные гиперссылки, доказательства, отчётный документ, цель, критерии приёмки и проверяемые артефакты.

Markdown можно оставить как человекочитаемый рендер, но **источником истины должен быть JSON**.

---

# 1. Основные принципы новой JSON-системы

1. **Задача** описывается JSON-объектом `tdl.task`.
2. **Отчёт исполнителя** описывается JSON-объектом `tdl.report`.
3. **Вердикт контролёра** описывается JSON-объектом `tdl.verdict`.
4. Каждое выполненное действие должно иметь:
   - ссылку на файл, commit, лог, тест, артефакт;
   - метрику «до/после»;
   - команду проверки;
   - результат проверки.
5. Статус задачи по TDL остаётся простым:
   - `open` — открыто;
   - `done` — выполнено.
6. Технологическое состояние задачи хранится отдельно в `workflow_state`:
   - `issued`;
   - `in_progress`;
   - `blocked`;
   - `reported`;
   - `control`;
   - `verified`;
   - `rejected`;
   - `archived`.
7. Задача может получить `status = done` только если:
   - существует `tdl.report`;
   - отчёт содержит доказательства;
   - существует `tdl.verdict`;
   - вердикт имеет `result = pass`.

# 2. Структура файлов и каталогов

Рекомендуемая структура:

```text
Tasks/
  JSON/
    Active/
      A-01.task.json
      A-02.task.json
    Reports/
      A-01_2026-08-06.report.json
    Verdicts/
      A-01_2026-08-06.verdict.json
    Index/
      tdl.index.json
```

Правила именования:

```text
{task_id}.task.json
{task_id}_{YYYY-MM-DD}.report.json
{task_id}_{YYYY-MM-DD}.verdict.json
```

Требования:

- кодировка UTF-8;
- даты в ISO 8601: `YYYY-MM-DD`;
- дата-время: `YYYY-MM-DDTHH:MM:SSZ`;
- комментарии внутри JSON запрещены;
- все ссылки должны быть в полях `href`, `path`, `url` или `ref`.

# 3. Статусы и lifecycle

## 3.1. TDL-статус

```json
["open", "done"]
```

## 3.2. Workflow state

```json
[
  "issued",
  "in_progress",
  "blocked",
  "reported",
  "control",
  "verified",
  "rejected",
  "archived"
]
```

## 3.3. Соответствие

| workflow_state | TDL status |
|---|---|
| `issued` | `open` |
| `in_progress` | `open` |
| `blocked` | `open` |
| `reported` | `open` |
| `control` | `open` |
| `rejected` | `open` |
| `verified` | `done` |
| `archived` | `done` |

# 5. Маппинг старых Markdown-файлов на JSON

## 5.1. Task

| Старый Markdown | Новый JSON |
|---|---|
| `id: A-01` | `task_id` |
| `приоритет: высокий` | `priority` |
| `статус: verified` | `legacy_status`, а TDL `status` вычисляется отдельно |
| `постановщик: агент-менеджер` | `assignees.issued_by` |
| `исполнитель: subagent` | `assignees.executor` |
| `дата: 2026-08-06` | `dates.issued` |
| `источник_запроса` | `source.type` |
| `замечание` | `mission.name` |
| `Контекст` | `context` |
| `Требования` | `acceptance_criteria` |
| `Границы` | `constraints` |
| `Результат` | `artifacts` |
| `Ход работы` | `history` / `progress_log` |

## 5.2. Report

| Старый Markdown | Новый JSON |
|---|---|
| `ОТЧЁТ: A-01` | `report_id` |
| `Дата` | `date` |
| `Исполнитель` | `executor` |
| `Что было не так` | `problem` |
| `Что сделано` | `work_done` |
| `Доказательства` | `evidence` |
| `Числа до/после` | `metrics` |
| `Открытые вопросы / ограничения` | `open_questions` |
| `Как пересобрать/проверить` | `verification_commands` |

## 5.3. Verdict

| Старый Markdown | Новый JSON |
|---|---|
| `ВЕРДИКТ КОНТРОЛЁРА` | `entity_type = tdl.verdict` |
| `Общий вердикт` | `result`, `confidence` |
| `Механические проверки` | `checks` |
| `Доказательства исполнителя` | `evidence_review` |
| `Обязательные исправления` | `required_fixes` |
| `Примечания контролёра` | `notes` |

# 12. Обязательные автоматические проверки JSON

## 12.1. Проверки задачи

Проверять:

1. `schema_version` существует.
2. `entity_type` равен:
   - `tdl.task`;
   - `tdl.report`;
   - `tdl.verdict`.
3. `task_id` уникален.
4. `wbs_code` соответствует родителю.
5. `wbs_code` имеет глубину не больше 4.
6. `is_summary = false` для исполнительских задач.
7. `status` равен только `open` или `done`.
8. Для `status = done` существуют:
   - минимум один `report_ref`;
   - минимум один `verdict_ref`;
   - `verdict.result = pass`.
9. Для `task_kind = execution` заполнены:
   - `goal`;
   - `acceptance_criteria`;
   - `verification.commands`.
10. Для тестовых задач заполнены:
   - `test_inputs`;
   - `check_subject`;
   - ожидаемые метрики.

## 12.2. Проверки отчёта

Проверять:

1. `task_ref` существует.
2. `work_done` не пуст.
3. `evidence` не пуст.
4. Каждое доказательство имеет:
   - `evidence_id`;
   - `type`;
   - `result`;
   - ссылку, команду или артефакт.
5. Если `exit_code != 0`, должно быть:
   - `acceptance_rule`;
   - baseline;
   - объяснение.
6. `metrics` содержат показатели до/после.
7. `verification_commands` не пуст.
8. `open_questions` может быть пустым, но поле обязательно.

## 12.3. Проверки вердикта

Проверять:

1. `task_ref` существует.
2. `report_ref` существует.
3. `checks` не пуст.
4. Каждая проверка имеет:
   - `check_id`;
   - `name`;
   - `status`;
   - `expected`;
   - `actual`.
5. Если `result = pass`, все критичные проверки должны быть `pass`.
6. Если `result = fail`, массив `required_fixes` не должен быть пуст.
7. Если `result = pass`, задача может быть переведена в `status = done`.

# 13. Правила закрытия задачи

Задача закрывается только так:

```text
task.status = done
```

если одновременно:

```text
report exists
report.evidence not empty
verdict exists
verdict.result = pass
verdict.can_move_forward = true
```

Если хотя бы одно условие не выполняется:

```text
task.status = open
```

Если есть блокировка:

```text
task.workflow_state = blocked
task.blocker = "причина"
```

# 15. Связь с текущей системой ProjectTDL

Если импортировать эти JSON в существующую Django-модель `ProjectTDL.TaskNode`, рекомендуется такое соответствие.

| JSON TDL | ProjectTDL / целевое поле |
|---|---|
| `task_id` | отдельное поле `external_task_id` |
| `wbs_code` | отдельное поле `wbs_code` |
| `parent_wbs` | родитель через `parent` / MPTT |
| `project.code` | `project_site` |
| `module` | отдельное поле `module_name` |
| `class_name` | отдельное поле `class_name` |
| `layer` | отдельное поле `layer` |
| `name` | `TaskNode.name` |
| `description` | `TaskNode.description` |
| `status` | `TaskNode.status`, только `Открыто` / `Выполнено` |
| `workflow_state` | отдельное поле `workflow_state` |
| `dates.start` | отдельное поле `start_date` |
| `dates.finish` | `TaskNode.due_date` |
| `links` | JSONField `links` |
| `artifacts` | JSONField `artifacts` |
| `evidence` из report | JSONField `evidence` |
| `verification.commands` | JSONField `verification_commands` |
| `history` | отдельная audit-модель или JSONField |
| `TaskDueDateHistory` | использовать для истории изменения `dates.finish` |

Если миграцию схемы делать пока нельзя, минимально допустимый вариант:

- `name` = наименование;
- `description` = JSON или markdown, сгенерированный из JSON;
- `due_date` = `dates.finish`;
- ссылки и доказательства хранить в `description` или отдельном JSON-поле, если оно доступно.

Но для полноценной фильтрации лучше вынести поля в отдельные колонки БД.

# 17. Итог

Новая схема заменяет свободный Markdown на управляемый JSON-конвейер:

```text
A-XX.task.json
   ↓
A-XX_YYYY-MM-DD.report.json
   ↓
A-XX_YYYY-MM-DD.verdict.json
   ↓
task.status = done
```

Для `A-01` этот конвейер уже можно считать корректно перенесённым в JSON: задача, отчёт и вердикт связаны, доказательства присутствуют, TDL-статус может быть `done`.

Для `A-02` корректная миграция такая:

```json
{
  "status": "open",
  "workflow_state": "pending_report",
  "legacy_status": "verified"
}
```

пока не будут созданы полноценные `A-02.report.json` и `A-02.verdict.json`.
