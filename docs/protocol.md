# Протокол конвейера dev-pipeline (обобщённый)

Версия: 1.0 (2026-08-06). Обобщено из `Tasks\00_Протокол_агентов.md` (HeatLossRevit2).
Применимо к любому проекту, подключённому через `examples\<project>\pipeline.yaml`.

## 0. Принципы

1. **Файлы + git = источник правды** по задачам (`Tasks\Активные\`, `Tasks\Отчёты\`,
   `Tasks\Архив\`). Сервер хранит только координацию: события, сообщения, heartbeat.
2. **Обмен — только артефактами и событиями**: агенты НЕ общаются в чате напрямую.
3. **Доказательства обязательны**: «собрал/запустил/проверил» — только с выводом команды
   (msbuild EXIT 0, vstest N/M, grep, diff).
4. **Сервер — push** (SSE) с фолбэком на файлы: сервер недоступен → файловые флаги
   в `Tasks\Конвейер\Уведомления\`.

## 1. Роли

| Агент | Роль | Что делает |
|---|---|---|
| Агент-1 | Контролёр/планировщик | задачи (dispatch), приём отчётов, вердикты (verify), оркестрация |
| Агент-2 | Исполнитель (Worker) | выполняет задачи A-NN, пишет отчёты с доказательствами |
| Агент-3 | Браузерный мост | передаёт промпты в облачный ИИ (Qwen/DeepSeek) и ответы обратно |
| Агент-4 | Облачный ИИ | тяжёлые ТЗ/анализ по контексту (через Агента-3) |

Правило: исполнитель и контролёр — НЕ один агент в одной сессии. Контролёр не правит
артефакты исполнителя — только фиксирует вердикт и список исправлений.

## 1.1. Подключение нового проекта (обязанность агента)

Если ты получил ссылку на dev-pipeline и задачу «вести проект <Имя>» — зарегистрируй его:
1. Создай `examples\<имя>\pipeline.yaml` (имя = латинская папка проекта): `project.name/root/branch`,
   `tasks.*`, `build` (msbuild/dotnet/none), `tests` (runner vstest|dotnet|pytest|none,
   `baseline_passed/baseline_total` — реальные цифры после прогона),
   `plan:` (repo/subdir/file — план в ProjectsPalns), `runner:` (модель, ретраи,
   таймаут вопросов, чекпоинты этапов), `checks`/`layer_rules` — только проходящие.
2. Проверь: `python -m pipeline.cli list` → проект в списке; `python -m pipeline.cli status <имя>` → без ошибок.
3. Проверь сборку/тесты из конфига и панель: `/api/projects` и `/api/tasks?project=<имя>` без 404.
4. Коммит `project/<имя>: регистрация в конвейере`, пуш по указанию пользователя.
5. Нет `Tasks\` у проекта — не создавай принудительно (панель терпима к пустым папкам);
   внешние отчёты проекта могут лежать в `pipeline_output\<имя>\` — упоминай путь в отчётах.

Шаблоны: `examples\heatlossrevit2\pipeline.yaml` (полный) / `examples\AHUCalculator\pipeline.yaml` (лёгкий).

## 2. Структура Tasks (у проекта)```
Tasks\
  00_Протокол_агентов.md           <- этот файл (обобщённый, в dev-pipeline\docs\)
  00_Контролёр_промпт\             <- промпт контролёра
  00_Референсы\                    <- справочные материалы
  Входящие\                        <- запросы (не оформленные задачи)
  Активные\                        <- открытые задачи (open/in_progress)
  Отчёты\                          <- отчёты исполнителей + вердикты
  Архив\                           <- закрытые задачи (только контролёр переносит)
  Конвейер\                        <- Уведомления\ (фолбэк), сторожевые скрипты
  Конвейер\Браузер\                <- задания Агенту-3 (опция)
```

## 3. Жизненный цикл задачи

```
ПОСТАНОВКА:  Активные\A-NN_имя.md      (статус: open)
ИСПОЛНЕНИЕ:  тот же файл                (in_progress)
ОТЧЁТ:       Отчёты\A-NN_Отчёт_<дата>  (done_report)
ПРОВЕРКА:    Отчёты\A-NN_Вердикт_<дата>(verified / rejected)
ЗАКРЫТИЕ:    перенос в Архив           (closed)
```

## 3.1. Жизненный цикл карточки плана (план-раннер, v2 — основной сценарий)

Источник истины — файл плана в ProjectsPalns (`<Проект>\_current\*.md`, статусы
карточек «Открыто/Выполнено» в самом файле):

```
ВЫБОР:      первая карточка со статусом open и закрытыми зависимостями
ПОСТАНОВКА: Активные\<CARD>_*.md (генерирует раннер из карточки)
GRILL:      субагент изучает код/вики; блокирующие вопросы -> Вопросы\<CARD>_*.md
            + wait_answer.py (таймаут 20 мин -> работа по допущениям ASSUMPTION)
ИСПОЛНЕНИЕ: правки -> сборка/тесты -> отчёт Отчёты\<CARD>_Отчёт_<дата>.md -> коммит plan/<CARD>
ПРОВЕРКА:   механический вердикт Отчёты\<CARD>_Вердикт_*  (сборка+тесты+checks)
ЧЕКПОИНТ:   метка «Чекпоинт: да» или конец этапа -> пауза до одобрения в панели
ЗАКРЫТИЕ:   статус done в файле плана + коммит в ProjectsPalns (`plan/<CARD>: …`)
```

Ретраи: FAIL вердикта → повтор с хвостом лога ошибки (≤ `runner.retries`) →
событие card_failed и стоп до вмешательства владельца.

## 4. Шаблон задачи

```markdown
---
id: A-<NN>
приоритет: высокий|средний|низкий
статус: open|in_progress|done_report|verified|rejected|closed
постановщик: контролёр
исполнитель: worker|qwen
зависимости: <A-NN или нет>
---
# ЗАДАЧА: <название>
## Контекст
## Цель
## Требования (критерии приёмки)
## Границы (что НЕ делать)
## Результат (куда положить артефакты)
## Ход работы (заполняет исполнитель)
```

## 5. Отчёт исполнителя (обязательные секции)

1. `# ОТЧЁТ: <A-NN> — <кратко>` + дата + статус (done/partial/blocked).
2. **Что было не так** (факты с цифрами).
3. **Что сделано** — по пунктам, с путями файлов и коммитами.
4. **Доказательства** — выводы сборки/тестов/grep, diff, сэмплы.
5. **Числа до/после**.
6. **Открытые вопросы и ограничения** (NEED_DATA, если данных нет).
7. **Как пересобрать/проверить** (команды).

## 6. Вердикт контролёра

PASS / FAIL / PARTIAL / NEED_DATA + таблица проверок (ID | Проверка | Ожидание | Факт |
Вердикт | Доказательство | Что исправить) + обязательные исправления перед закрытием.

## 7. Git-дисциплина

### 7.1. Префиксы коммитов (обязательные)

Репозиторий **dev-pipeline**:

| Префикс | Что кладёт |
|---|---|
| `pipeline: <суть>` | каркас конвейера (код/тесты/хотфиксы) |
| `project/<имя>: <суть>` | конфиги примеров `examples\<имя>\` |
| `agent/A-NN: <суть>` | исполнитель задач A-NN |
| `review/A-NN: <суть>` | контролёр |
| `inbox: <суть>` | сырые задания |
| `docs: <суть>` | документация |

Репозиторий **ProjectsPalns**:

| Префикс | Что кладёт |
|---|---|
| `plans: <Проект>: <суть>` | планы/статусы/ревью/HANDOFF проекта |
| `plan/<CARD>: <суть>` | закрытие карточки (done) или постановка новой |
| `docs: <суть>` | служебные документы |

Легаси-префиксы истории (`feat:`, `fix:`, `chore:`, `ui:`, `server:`, `agents:`,
`tdl:`, `tools:`, `config:`, `security:`, `dashboard:`, `skills:`, `manager:`,
`init:`, `brief …:`, `verify…:`) парсер распознаёт как отдельную группу — новые
коммиты с ними не создаются.

Тема — до 80 символов, по-русски, суть без деталей.

### 7.2. Привязка к карточке

В теле коммита по карточке указывается трейлер `Refs: <CARD>` (можно несколько,
через запятую). Коммит статуса в плане уже несёт `<CARD>` в префиксе
(`plan/<CARD>:`) — дублировать Refs там не нужно.

### 7.3. Ветки

| Ветка | Назначение | Срок жизни |
|---|---|---|
| `main` | рабочая правда: только зелёные тесты | постоянная |
| `exp/<slug>` | эксперимент владельца/рискованная идея | ≤ 3 дней → слить `--no-ff` или удалить |
| `fix/<slug>` | горячий фикс вне плана | часы → слить после проверки |

Числовые имена веток запрещены. Мёртвые ветки удаляются, живые переименовываются
(`git branch -m старое exp/новое`).

### 7.4. Версии-якоря (теги)

- `stage/<N>-done` — этап плана принят (ставит план-раннер при approver=reviewer
  или владелец вручную);
- `cp/<CARD>` — чекпоинт одобрен;
- `vX.Y` — релизная точка владельца (семантика: X = ломающие изменения, Y = новое).

Старые числовые теги не удаляются (история), но новые якоря — только семантичные.

### 7.5. Параллельные сессии

В общих репозиториях (ProjectsPalns) запрещён `git add -A` / `commit -a` —
только явные пути своих файлов. Инциденты 2026-08-23: чужие незакоммиченные
правки попадали в чужие коммиты (b1089c8, d498c3e).

- НЕ коммитить: `.idea\`, `.opencode\`, `bin\obj`, `TestResults\`, `__pycache__\`,
  `*.db`, логи, мусорные txt.
- Один артефакт = один коммит.

## 8. Сообщения через сервер (SSE) и фолбэк

- События/сообщения — через сервер (`/events`, `/messages`, `/heartbeat`). См. `architecture.md`.
- Фолбэк: сервер недоступен → файлы `Tasks\Конвейер\Уведомления\` (как в v1 HeatLossRevit2).

## 8.1. Сырые задания пользователя (Входящие)

Сырое задание — заявка пользователя, ещё не оформленная в задачу A-NN. Правила:

1. **Создание**: через dashboard («📥 Входящие») — текст (Markdown) → кнопка «➕ Создать и сохранить».
   Или напрямую: `POST /api/requests` `{project, text}`.
2. **Хранение (источник правды — файлы+git)**:
   - файл: `Tasks\Входящие\{R-XXXX}_{slug}.md` (заголовок `# Сырое задание {id}`, метаданные, `## Задание`);
   - запись в БД сервера (таблица `requests`: id, project, text, status, file, commit_sha);
   - git-коммит в проекте: `inbox: сырое задание {id} ({file})`.
3. **Список/чтение**: dashboard «📥 Входящие» (список: id, статус, дата, путь к файлу; кнопки
   «📄 Читать» — редактор с Markdown-предпросмотром, «📋 Путь» — копирование полного пути к файлу).
   API: `GET /api/requests`, `GET /api/requests/{id}` (возвращает `path` — полный путь к файлу).
4. **Редактирование**: в редакторе задания (textarea + живой предпросмотр) → «💾 Сохранить»
   (`PATCH /api/requests/{id}`): перезапись файла, git-коммит `inbox: обновлено задание {id}`, обновление БД.
5. **Оформление в задачу (dispatch)**: контролёр — кнопка «📋 Оформить» (`POST /api/requests/{id}/dispatch`)
   → файл уходит в `Tasks\Активные\` как задача; статус → `dispatched`.
   ВАЖНО: при запущенном `agent_watch --watch-dispatch` Входящие оформляются автоматически
   (поллинг раз в 30 с) — для ручного управления остановите watch.
6. **Статусы**: `new` → `dispatched`. Идемпотентность: повторный dispatch не создаёт дублей.
7. **Маркдаун-редактор**: рендер предпросмотра — функция `renderMarkdown` из
   `D:\Projects\LocalAssitent\webui\static\app.js` (используется в dashboard).

## 8.2. Безопасность: рестарт агентов только по белому списку

`POST /heartbeat` доступен любому локальному процессу без авторизации, поэтому поле
`cmd` в нём — недоверенный ввод. Правила (с 2026-08-23):

1. **Белый список** `AGENT_LAUNCH_COMMANDS` задан в коде `server/app.py`
   (имя агента → argv): executor, plan-runner, controller, browser, agent-manager.
2. `POST /heartbeat` сохраняет `cmd` в БД **только для имён из белого списка**;
   для остальных поле игнорируется (`restartable = false`).
3. `POST /api/chat/agents/{name}/restart`:
   - имя вне белого списка → **403**;
   - сохранённая команда сравнивается с канонической строкой реестра **дословно**
     (после strip) — не совпала → **403**; пустая → **404**;
   - исполняется строго argv из реестра (не разобранная строка из БД).
4. Следствие: произвольная команда, подложенная через `/heartbeat`, исполнена быть
   не может; чтобы добавить нового перезапускаемого агента — расширьте реестр в коде.

## 8.3. Паузы и межагентные передачи (контракт видимости)

Панель показывает ❓/⏸ из файлов (`Tasks\Вопросы\*.md`,
`Tasks\Конвейер\checkpoints\*.pending.json`), а не из чата. Правила для ЛЮБОГО
агента (с 2026-08-23):

1. Перед паузой сделай её видимой:
   - вопрос владельцу → файл `Tasks\Вопросы\<CARD>_<время>.md`
     (+ блокировка `agents/wait_answer.py`);
   - ожидание решения по карточке → `agents/checkpoint.py create <project> <CARD>
     --reason ...`, затем `agents/checkpoint.py wait <project> <CARD> [--timeout N]`.
2. Оформил карточку в плане для ДРУГОГО агента → доставь сам:
   `agents/checkpoint.py handoff <project> <CARD> --to <agent> --text "..."`
   (сообщение адресату + событие task_handoff в ленту). Владелец не курьер.
3. Watchdog: раннер в фазе checkpoint дольше `checkpoint_remind_sec*2` без
   pending-файла → событие `checkpoint_orphan`.

Автопродолжения нет: решение — только файл decision.json от владельца/ревьюера.

## 9. Антипаттерны (запрещено)

- «Сделано, всё ок» без отчёта и доказательств.
- Правка чужих отчётов/вердиктов; удаление из Архива без согласования.
- «Подгонка» результата под ожидаемый ответ.
- Устные решения вместо записей в файле задачи.
- Применение ответа облачного ИИ без проверки полноты и без сборки.
