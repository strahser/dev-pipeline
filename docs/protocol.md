# Протокол конвейера dev-pipeline (обобщённый)

Версия: 1.0 (2026-08-06). Обобщено из `Tasks\00_Протокол_агентов.md` (HeatLossRevit2).
Применимо к любому проекту, подключённому через `examples\<project>\pipeline.yaml`.

## 0. Принципы

1. **Файлы + git = источник правды** по задачам (`Tasks\Активные\`, `Tasks\Отчёты\`,
   `Tasks\Архив\`). Сервер хранит только координацию: события, сообщения, heartbeat.
2. **Обмен — только артефактами и событиями**: агенты НЕ общаются в чате напрямую.
3. **Доказательства обязательны**: «собрал/запустил/проверил» — только с выводом команды
   (msbuild EXIT 0, vstest N/M, grep, diff).
4. **Сервер — push** (SSE) с фолбэком на файлы: сервер недоступен → файловые флаги
   в `Tasks\Конвейер\Уведомления\`.

## 1. Роли

| Агент | Роль | Что делает |
|---|---|---|
| Агент-1 | Контролёр/планировщик | задачи (dispatch), приём отчётов, вердикты (verify), оркестрация |
| Агент-2 | Исполнитель (Worker) | выполняет задачи A-NN, пишет отчёты с доказательствами |
| Агент-3 | Браузерный мост | передаёт промпты в облачный ИИ (Qwen/DeepSeek) и ответы обратно |
| Агент-4 | Облачный ИИ | тяжёлые ТЗ/анализ по контексту (через Агента-3) |

Правило: исполнитель и контролёр — НЕ один агент в одной сессии. Контролёр не правит
артефакты исполнителя — только фиксирует вердикт и список исправлений.

## 2. Структура Tasks (у проекта)

```
Tasks\
  00_Протокол_агентов.md           <- этот файл (обобщённый, в dev-pipeline\docs\)
  00_Контролёр_промпт\             <- промпт контролёра
  00_Референсы\                    <- справочные материалы
  Входящие\                        <- запросы (не оформленные задачи)
  Активные\                        <- открытые задачи (open/in_progress)
  Отчёты\                          <- отчёты исполнителей + вердикты
  Архив\                           <- закрытые задачи (только контролёр переносит)
  Конвейер\                        <- Уведомления\ (фолбэк), сторожевые скрипты
  Конвейер\Браузер\                <- задания Агенту-3 (опция)
```

## 3. Жизненный цикл задачи

```
ПОСТАНОВКА:  Активные\A-NN_имя.md      (статус: open)
ИСПОЛНЕНИЕ:  тот же файл                (in_progress)
ОТЧЁТ:       Отчёты\A-NN_Отчёт_<дата>  (done_report)
ПРОВЕРКА:    Отчёты\A-NN_Вердикт_<дата>(verified / rejected)
ЗАКРЫТИЕ:    перенос в Архив           (closed)
```

## 4. Шаблон задачи

```markdown
---
id: A-<NN>
приоритет: высокий|средний|низкий
статус: open|in_progress|done_report|verified|rejected|closed
постановщик: контролёр
исполнитель: worker|qwen
зависимости: <A-NN или нет>
---
# ЗАДАЧА: <название>
## Контекст
## Цель
## Требования (критерии приёмки)
## Границы (что НЕ делать)
## Результат (куда положить артефакты)
## Ход работы (заполняет исполнитель)
```

## 5. Отчёт исполнителя (обязательные секции)

1. `# ОТЧЁТ: <A-NN> — <кратко>` + дата + статус (done/partial/blocked).
2. **Что было не так** (факты с цифрами).
3. **Что сделано** — по пунктам, с путями файлов и коммитами.
4. **Доказательства** — выводы сборки/тестов/grep, diff, сэмплы.
5. **Числа до/после**.
6. **Открытые вопросы и ограничения** (NEED_DATA, если данных нет).
7. **Как пересобрать/проверить** (команды).

## 6. Вердикт контролёра

PASS / FAIL / PARTIAL / NEED_DATA + таблица проверок (ID | Проверка | Ожидание | Факт |
Вердикт | Доказательство | Что исправить) + обязательные исправления перед закрытием.

## 7. Git-дисциплина

- Коммиты: `agent/A-NN: ...` (исполнитель), `review/A-NN: ...` (контролёр),
  `browser: ...` (Агент-3), `docs: ...` (служебные).
- НЕ коммитить: `.idea\`, `.opencode\`, `bin\obj`, `TestResults\`, мусорные txt.
- Один артефакт = один коммит.

## 8. Сообщения через сервер (SSE) и фолбэк

- События/сообщения — через сервер (`/events`, `/messages`, `/heartbeat`). См. `architecture.md`.
- Фолбэк: сервер недоступен → файлы `Tasks\Конвейер\Уведомления\` (как в v1 HeatLossRevit2).

## 9. Антипаттерны (запрещено)

- «Сделано, всё ок» без отчёта и доказательств.
- Правка чужих отчётов/вердиктов; удаление из Архива без согласования.
- «Подгонка» результата под ожидаемый ответ.
- Устные решения вместо записей в файле задачи.
- Применение ответа облачного ИИ без проверки полноты и без сборки.
